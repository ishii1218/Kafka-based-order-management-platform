3. Architecture diagram

“This diagram shows the complete event flow. The producer creates normal and controlled failure orders. Each order is encoded into Avro binary and published to the partitioned Kafka orders topic. The consumer decodes and validates it. Successful orders update an incremental running average. Temporary failures enter bounded exponential retry. Permanent failures and exhausted retries are encoded with diagnostic metadata and written to the orders-dlq topic. The source offset is committed only after successful processing or an acknowledged DLQ write.”

How to explain every architecture component

ComponentWhat it doesTheory to mention
ProducerCreates 10 random orders and three controlled failure cases.Producers publish events without directly depending on consumers.
Avro encoderUses order.avsc to turn a Python dictionary into compact bytes.Schema-based serialization creates a typed producer-consumer contract.
ordersStores records across three partitions using orderId as the key.Partitions enable parallelism; ordering is guaranteed only inside a partition.
ConsumerPolls messages, decodes Avro and performs validation and processing.A consumer group tracks work through partition offsets.
Running averageUpdates count and total for each successful order.Incremental stream aggregation uses O(1) state per update.
Retry engineRetries temporary failures after 0.5, 1 and 2 seconds.Bounded exponential backoff gives dependencies time to recover without infinite retry.
DLQPreserves permanent and retry-exhausted messages with error metadata.A Dead Letter Queue isolates poison messages for diagnosis or reprocessing.
Manual commitCommits only after success or confirmed DLQ publication.This avoids acknowledging a record before its outcome is safely handled.

7. Core theory to explain

Kafka topic, partition, key and offset

“A Kafka topic is a named event stream. A partition is an ordered section of that stream and allows work to scale in parallel. The order ID is the message key, so messages with the same key are routed consistently. An offset is a message’s position inside one partition. A consumer group coordinates which consumer owns each partition and remembers processing progress through committed offsets.”

Why Kafka is appropriate for big data

“Kafka is designed for continuous high-velocity event ingestion. It decouples producers and consumers, stores events durably, supports replay and scales throughput through partitions. This demonstration uses a small number of orders, but the architecture represents a scalable streaming system.”

Why Avro instead of plain JSON

“Avro provides compact binary encoding and explicit typed schemas. The schema prevents arbitrary message structures and forms a clear contract between producer and consumer. This project deploys the schema files with both applications. A larger system could add a Schema Registry for independent version discovery and compatibility control.”

Why exponential backoff

“Immediate repeated retries can overload an already failing dependency. Exponential backoff increases the delay after each failure. Bounded retries also guarantee that one message does not retry forever.”

Why a Dead Letter Queue

“A poison message should not block the main stream or disappear silently. The DLQ isolates it, preserves the original business data and adds diagnostic information for later inspection, correction or controlled reprocessing.”

Delivery semantics

“The design is at-least-once oriented, not exactly-once. Manual offset commits reduce message-loss risk because the source offset is recorded only after success or DLQ delivery. However, a crash after processing but before the commit can cause Kafka to replay the event, so duplicate processing remains possible.”

8. Honest limitations and production improvements

Current demonstrationProduction improvement
One Kafka brokerUse multiple brokers, replicated partitions and appropriate minimum in-sync replicas.
Average stored in consumer memoryUse Kafka Streams, Flink, ksqlDB or an external durable state store.
Retry sleeps inside the consumerUse delayed retry topics so one failed record does not pause its partition.
Schemas deployed with applicationsAdd a Schema Registry with compatibility policies.
No authentication or encryptionAdd TLS, SASL, access-control lists and secret management.
At-least-once behaviorUse transactional processing or idempotent state updates where exact outcomes are required.
No production observabilityAdd metrics, centralized logs, lag monitoring and alerts.
“The running average is local and resets when the consumer restarts. Multiple consumers would also calculate separate partial averages. In production I would use durable, partition-aware stream state. The retry loop intentionally simplifies the demonstration; delayed retry topics would improve throughput. The single broker proves functionality but does not provide broker-level fault tolerance.”

9. Likely viva questions

QuestionShort answer
Why not send orders directly to the consumer?Kafka decouples services, buffers events, supports replay and permits independent scaling.
Why is orderId the key?It provides stable partition selection and preserves ordering for events belonging to that order.
Why are failed orders excluded from the average?Only successfully processed business transactions should change the valid analytic result.
What does acks=all mean here?The producer waits for acknowledgement from all currently required in-sync replicas; this one-broker demo has only one replica.
Does idempotence make the whole system exactly-once?No. It reduces producer duplicates, but application processing and state updates can still repeat after a crash.
Why not retry permanent failures?The same invalid data will fail again, wasting resources and delaying useful work.
What happens if the consumer restarts?Kafka resumes from committed offsets, but this demo’s in-memory running average resets.
Why may logs appear in a different order?Kafka ordering is per partition. The topic has three partitions, so cross-partition order is not global.
What is KRaft?Kafka’s built-in metadata and controller consensus architecture, replacing the need for ZooKeeper.
